# ADR-003 — Déploiement continu par PR et durcissement de l'espace de noms (phase 4.3)

- Statut : accepté, 2026-11-09
- Contexte : ADR-002 en place (CRM 0.2.0 sur `https://app.tramelya.es`). Un `git tag vX.Y.Z` dans le CRM publie des images signées sur GHCR, mais **rien ne change dans le cluster** tant que quelqu'un n'édite pas `image.tag` ici : Argo CD suit Git, jamais GHCR. Un seul nœud k3s de 8 Go, données fictives. Pods déjà non-root, sans capacité, avec requêtes et limites (ADR-002 §11).

## Décisions

1. **CD par pull request.** À la fin de `release.yml` du CRM, un job `gitops-pr` écrit la version (`image.tag`) **et l'empreinte de chaque image** (`image.digests`) dans `clusters/demo/acrm-demo.yaml`, sur une branche `release/vX.Y.Z`, et ouvre une PR. **Merger = déployer** ; revert = revenir en arrière. La CI de ce dépôt (rendu Helm, kubeconform, Trivy) passe sur la PR avant le merge. Écarté : **Argo CD Image Updater** (un contrôleur de plus, qui écrit lui-même dans Git avec ses propres droits et surveille le registre : moins lisible qu'une PR, et une signature de plus à gérer) ; commit direct sur `main` (pas de relecture, et la CI passerait après coup).
2. **Merge manuel** sur la démo. L'auto-merge (« merger dès que la CI est verte ») est possible plus tard en une option du dépôt ; il retire le seul point où un humain choisit le moment du déploiement (ex. pas pendant une démo).
3. **Images tirées par empreinte** (`acrm-api:0.3.0@sha256:…`). Un tag GHCR peut être déplacé, une empreinte non : le cluster exécute exactement l'image que Trivy a scannée et que cosign a signée. Le tag reste écrit pour la lecture humaine. Le chart refuse une empreinte mal formée (`fail` au rendu). Les releases antérieures à 4.3 (0.2.0) restent tirées par tag.
4. **Jeton : une GitHub App** (« tramelya-gitops-bot ») installée sur ce SEUL dépôt, droits `contents: write` + `pull_requests: write`. Jeton d'une heure, créé et révoqué par le job (`actions/create-github-app-token`). Écarté : PAT (lié au compte de Paul, longue durée, souvent trop large) ; `GITHUB_TOKEN` (limité au dépôt du CRM, et une PR qu'il ouvre ne déclenche pas la CI d'un autre dépôt). Identifiant de l'App dans une **variable** du dépôt CRM (`GITOPS_APP_CLIENT_ID`, non secrète), clé privée dans un secret de l'**environnement `release`** limité aux tags `v*` (`GITOPS_APP_PRIVATE_KEY`) : un autre workflow ou une branche ne peut pas obtenir de jeton. `main` de ce dépôt exige une PR et la CI verte, sans exception pour l'App : le robot **propose**, il ne pousse jamais sur la branche qu'Argo CD applique. Sans la variable, le job est sauté (la release reste valable). Relancer le job pour une même version réécrit la branche `release/vX.Y.Z` (`--force`) : une retouche manuelle serait à refaire.
5. **Un seul environnement `demo`, déployé sur tag.** Le PLAN prévoyait staging à chaque merge et prod à chaque tag ; sur un nœud de 8 Go, un second CRM complet (base, Redis, API, worker) ne tient pas sans retirer de la marge à la démo, et une démo n'a pas d'utilisateur à protéger d'une régression. Staging et prod séparés : avec le premier client payant (plusieurs nœuds, ADR-001 asesoria-infra).
6. **NetworkPolicies : tout interdit par défaut** dans `acrm-demo` (entrée ET sortie), puis une politique par flux (`charts/acrm/templates/networkpolicy.yaml`) : Traefik → web 8080 / api 3000 ; api et worker → base 5432, Redis 6379, Mailpit 1025, Internet en 443 **hors plages privées et adresse de métadonnées** ; migrate et seed → base ; opérateur CloudNativePG → base 5432 / 8000 ; base → API Kubernetes (6443, l'IP du nœud change à chaque reconstruction : seul le port est restreint) ; tous → DNS. Le front n'émet rien. Risque accepté : les pods de la base peuvent joindre n'importe quelle adresse sur le seul port 6443 (l'IP du nœud n'est pas connue du chart). Appliquées par le contrôleur intégré à k3s (kube-router). Vérifiées hors cluster par un simulateur (40 flux) puis sur le cluster (étape 12 du runbook).
7. **Pod Security `restricted` imposé** à l'espace de noms (`enforce`, `warn`, `audit`, version `latest`), par un `Namespace` décrit dans Git (`apps/acrm-demo/namespace.yaml`, vague -2, `Prune=false,Delete=false` : retirer le fichier ou l'Application ne supprime jamais l'espace de noms ni la base). Vérifié AVANT le merge par `kubectl label --dry-run=server`, qui liste les pods existants qui seraient refusés.
8. **AppProject `acrm`** : l'Application du CRM ne peut lire que ce dépôt, n'écrire que dans `acrm-demo`, et ne créer qu'un seul objet de cluster (le `Namespace`). Les autres Applications (plateforme) restent dans `default` : elles installent des CRD et des rôles de cluster.
9. **Pas de PodDisruptionBudget ni de HPA** sur la démo : avec 1 réplique sur 1 nœud, un PDB `minAvailable: 1` bloquerait toute maintenance du nœud (`kubectl drain`), et un HPA n'a pas de second nœud où placer des copies. À faire en production (≥ 2 répliques de l'API, plusieurs nœuds). Requêtes et limites : déjà en place (ADR-002 §11) ; pas de limite CPU volontairement (elle bride l'API sans protéger la mémoire).

## Conséquences

- Déployer = `git tag -a vX.Y.Z` dans le CRM → attendre la release → relire et merger la PR `deploy(demo): acrm X.Y.Z` ici.
- Un nouveau besoin réseau (ex. SMTP sortant réel, IA en UE, Gmail) **doit** être ouvert dans `networkpolicy.yaml`, sinon il échoue en silence (délai dépassé) : c'est voulu.
- Restent : test de reconstruction chronométré (reporté, DoD de la phase 4), staging séparé et PDB / HPA en production, sauvegardes de la base (phase 5).
